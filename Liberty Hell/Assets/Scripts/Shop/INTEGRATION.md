# Item and shop integration

The shop is independent of scenes and UI. Create one `ItemInventory` and one `ShopService` per run, with an `IShopEconomy` implementation backed by the authoritative `RunState`. No such adapter exists yet: `RunState` currently has no atomic operation that changes money and blood together with an inventory grant before notifying observers. Do not combine its separate public mutation methods as a substitute. The run owner must provide the atomic operation and a revision that changes whenever relevant state changes. `Read()` supplies current money, blood, maximum blood, nominal bet and shop availability; `TryCommit` must reject stale revisions, invoke the supplied grant exactly once only on success, and publish the complete transaction before notifications. Serialize run, shop, reset and spin operations on the game thread; reject reentrant mutations during commit.

UI enumerates `ItemDefinition.All`, calls `CanPurchase(ItemId)` for a `PurchaseResult` with `Code`, `Message` and `Success`, and calls `TryPurchase(ItemId)` to revalidate and commit. `Inventory.CurrentEffects` and `Inventory.HasPendingGuarantee` are read-only views. Start a new run by calling `ItemInventory.ResetForNewRun()` alongside the authoritative run reset; it does not change resources. Spin IDs must be nonempty and unique within a run. Discard old spin requests when resetting a run.

For a spin, read `CurrentEffects` without consuming anything and use `GetSymbolWeightMultiplier` or `GetEffectiveWeight` with the original weights. Fractional weights must be represented without truncation: for integer sampling, scaling all base weights by two and multiplying X and Y by three instead of two when the lure is active preserves the exact ratios, subject to overflow validation. Use `GetEffectiveBetCost` for the charge; it rounds to the nearest integer with midpoints away from zero and a minimum of one. Continue to use the nominal bet for payout rules. Use `GetEffectiveLosingBloodLoss` only for loss caused by a losing spin; its fractions round down.

After the authoritative system has accepted a spin, call `ConfirmSpinStarted(Guid)` with its unique ID exactly at the agreed acceptance boundary and retain the returned `ItemEffects` with that spin. A repeat with the same ID returns the original snapshot and never consumes another guarantee. If `GuaranteedXXX` is true, evaluate `SlotSymbol.X, SlotSymbol.X, SlotSymbol.X` using the existing slot rules for that spin; do not replace the snapshot with a later inventory read. Failed validation or rejected starts must not call confirmation. The existing controller generates its result before it assigns an ID and declares a successful start, so it needs a coordinated change that makes acceptance, snapshot retention and result generation consistent; the integration is not connected by this module.
